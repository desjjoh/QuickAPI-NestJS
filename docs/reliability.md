# Reliability and recovery

[Documentation index](../README.md#documentation)

## Identity security and durable email

Authentication/registration/password-reset and account security/session controllers use `SecurityOperation`: their handler writes, success audits, and email intents commit in one application transaction. Refresh-cookie changes are staged until commit and credential responses have `Cache-Control: no-store`. Guards still execute before this boundary. OTP failure counters and lockout deliberately commit using the root manager after the request transaction releases its connection/locks, but before completing the response. Rejecting a code cannot roll back its security accounting, and failed requests do not monopolize the pool while waiting for another connection. Outside application transactions, accounting is immediate.

Security endpoints **reject `Idempotency-Key` with `400`**, rather than store and replay JWTs, reset authorizations, or refresh cookies. Challenges are single-use: a rolled-back operation may retry; a committed operation with a lost credential response requires fresh sign-in or a new challenge. Concurrent refresh requests using an old credential cannot both rotate the session: the handler locks and compares the persisted refresh hash. Clients must serialize refreshes and sign in again after an ambiguous committed rotation. CSRF/authentication/authorization and throttling continue to apply.

Apply all pending migrations from [the migration directory](../src/database/migrations) before deploying these services; use `npm run migration:show` rather than relying on historical migration filenames. EmailService compiles and inserts an AES-256-GCM-encrypted MySQL intent in the same transaction, without depending on Redis availability. A five-second dispatcher publishes only a UUID delivery ID; deterministic Bull job IDs prevent duplicate queued work. Pending intents are reconsidered every minute, including exhausted or completed jobs, until expiry. Workers lock the intent, supply the same delivery ID in provider metadata, and erase ciphertext on delivery, cancellation, or expiry. New challenges cancel pending intents for the same subject/template/purpose; challenge intent expiry matches the actual challenge expiry. Cancellation cannot recall a message already accepted by the provider.

All API/worker replicas must use the same stable `CRYPTO_SECRET`. Do not rotate it while encrypted pending intents remain: drain them or implement an explicit key-version migration first. Challenge email secrets and recipients are encrypted, cancellation scopes use keyed hashes, new Redis jobs contain only identifiers, and new delivery failures expose only a generic error. Legacy compiled-payload jobs are still supported for deployment draining; remove those legacy jobs/DLQ records according to the existing privacy policy. Restrict database, queue-dashboard, and backup access. Non-challenge intents expire after 24 hours; the sweep erases expired payloads and removes non-pending tombstones 24 hours after their original expiry, with possible sweep lag. Backups have separate retention.

Delivery is **at-least-once, not exactly-once**: provider acceptance followed by a timeout or a database commit failure can result in another send. The stable metadata identifier supports tracing, not a promise of provider-side deduplication. Monitor pending-intent age, expired/cancelled intent counts, worker failures and DLQ volume; alert before challenge expiry. Redis dispatch waits are bounded to avoid indefinitely retaining transaction locks. SMTP/provider outages can still delay or expire notification delivery.

## Durable storage lifecycle

Infrastructure belongs to `modules/system/storage` and `modules/system/storage-cleanup`: object transport, upload tracking and temporary-file sweeping live in storage, while deletion intents, reconciliation, queue producers, dispatchers, workers and DLQ handling live in storage-cleanup. The media domain imports these services and owns image validation/persistence only. Cleanup uses an injected `StorageReferenceReader`; media supplies its image repository at module composition, so cleanup infrastructure does not import domain repositories or modules.

Apply all pending deletion-intent and upload-tracking migrations before deploying API/workers. Tracking backfills existing image keys and deletion intents. Image replacement/removal writes a `storage_deletion_intents` row in the same transaction as the image change. Failed transactions leave no deletion obligation for the old/current object. Requests return once their database mutation, audit and replay state commit; cleanup is asynchronous and does not turn successful writes into `500` responses during a storage outage.

Every managed upload reserves a server-generated UUID key in `storage_objects` before contacting storage. Reservation and upload markers commit independently of the request transaction through a lazy auxiliary pool (two connections per application instance), so request rollback cannot erase crash-recovery information or starve a one-connection request pool. Include these connections in deployment sizing. PUT uses a 60-second abort deadline and holds the ownership row lock while active. Only an `uploaded` key can be attached, and attachment commits in the same transaction as image persistence. Keys are never reused; deleted ownership tombstones are retained.

A five-second dispatcher reconciles expired upload records, claims bounded intent batches and sends only intent IDs to BullMQ `storage-cleanup`. Dispatch happens outside SQL locks, uses bounded Redis waits, and reconsiders unfinished dispatch after a one-minute lease. Each worker locks the intent and ownership record, checks current image references, and commits a permanent attachment fence before deleting its exact recorded storage key. Attachment and cleanup serialize through the same ownership lock; cleanup runs outside request transactions to avoid stale request snapshots. Missing objects are safe to delete again; completed/blocked/failed intents are not executed again. This is at-least-once deletion: a crash after object deletion but before SQL completion can repeat the provider call without making the key attachable again.

Reconciliation skips locked active PUTs and finds unreferenced `reserved`/`uploaded` records after a 15-minute grace period. A known completed upload abandoned by rollback becomes eligible immediately; uncertain PUT outcomes keep the grace period. Claims and cleanup intents commit together, so concurrent reconcilers do not duplicate an obligation. After deletion, a delayed existence check catches a late provider write and schedules another deletion if necessary. Only an explicit HEAD `404` confirms absence; authentication/network/provider errors leave verification due for retry. This is bounded recovery for tracked uploads, not bucket-wide inventory: pre-existing untracked blobs and provider writes arriving after the delayed verification require a separate inventory/reconciliation policy. Remote storage and SQL do not form an atomic transaction.

Deletion has a durable five-attempt budget, with BullMQ exponential backoff starting at one second. Provider errors are sanitized before database/Redis persistence. Exhaustion marks the intent `failed`; the dispatcher forwards a deterministic, retained record to `storage-cleanup-dlq` and records successful forwarding. A failed DLQ handoff remains recoverable in SQL and does not restart object deletion. Failed intents are not automatically reset or purged. DLQ records contain only the stable intent ID, attempt count and fixed sanitized reason; the intent holds the originating request ID and exact storage key. These IDs support future ticket linkage. No ticket creation or administrator replay API is implemented yet; do not use direct Bull retries as a replacement for an authorized durable-state retry workflow.

Both queues are registered in the existing optional Bull Board dashboard. Restrict dashboard/table/backup access; storage keys and request IDs can be sensitive. Monitor pending intent age, blocked reference checks, terminal failures, DLQ forwarding failures and retained-record growth. The initial version deliberately retains terminal records for follow-up rather than choosing a support-ticket retention policy prematurely.

For rollout, pause/drain old upload writers before enabling the tracking-aware API and workers: all attachment writers must participate in the ownership protocol. Direct SQL imports or older code that bypasses attachment coordination are outside the concurrency guarantee. Preserve tracking tombstones and unfinished intents during rollback, and run compatible workers; do not revert/drop these tables with active uploads or unfinished cleanup. Future support-ticket linkage and authorized DLQ replay remain separate work.

## Storage failure and retry contract

[`storage-cleanup.contract.ts`](../src/modules/system/storage-cleanup/types/storage-cleanup.contract.ts) defines worker outcomes, fixed failure messages and retry/deadline policy. SQL is authoritative; BullMQ completion means a delivery was handled, **not necessarily that the object was deleted**. Inspect the durable intent's state when reporting cleanup status.

| Boundary/outcome                                          | Contract                                                                                                                                                                                                                                  |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Upload reservation fails                                  | No PUT begins. The HTTP mutation fails and does not create completed replay state.                                                                                                                                                        |
| PUT fails or times out after possible acceptance          | The HTTP operation returns a generic retryable `503`, never the provider's raw response; its independently committed reservation remains recoverable. An HTTP retry may upload to a new key, never overwrite the uncertain key.           |
| Image/audit/request transaction rolls back                | No committed image or old-object deletion obligation; newly uploaded objects are abandoned for asynchronous reconciliation. A crash before abandonment is covered by the reservation grace period.                                        |
| Image mutation commits while storage/Redis is unavailable | The successful HTTP response and keyed replay remain successful. Cleanup retries independently; replay does not upload, mutate, audit or schedule again.                                                                                  |
| DELETE fails or exceeds five seconds                      | Commit one sanitized provider-attempt failure, retain the attachment fence, and throw a sanitized worker error for backoff. The remote call may still finish; repeated deletion of this never-reused key is safe.                         |
| SQL fails before calling DELETE                           | No provider attempt is consumed. Pending SQL work is redispatched after the dispatch lease.                                                                                                                                               |
| Provider DELETE succeeds but SQL completion fails         | Pending work retries at least once; the separately committed fence survives. The rolled-back attempt counter cannot account for the already-finished remote call. Five attempts bounds committed accounting, not crash-time remote calls. |
| Current image references the key                          | Intent becomes `blocked`; no DELETE. It is not automatically reopened when the reference disappears; normal image removal schedules its own obligation.                                                                                   |
| Intent missing, `completed`, `blocked` or `failed`        | Worker acknowledges the delivery and returns that outcome without another provider call or budget reset. Stale jobs and direct Bull Board retries cannot revive terminal work.                                                            |
| Redis job removed/recreated, stalled or retried           | SQL retains the cumulative attempt budget. A fresh Redis job cannot authorize another five provider calls.                                                                                                                                |
| Automatic budget exhausted                                | SQL becomes `failed`; dispatch forwards a retained DLQ identity. DLQ processing never deletes, resets state or creates a ticket.                                                                                                          |
| DLQ publication or its SQL acknowledgement fails          | Retry publication using the same deterministic DLQ job ID. A repeated dispatch cannot create another failure identity.                                                                                                                    |
| Malformed cleanup/DLQ payload                             | Fail as unrecoverable without storage access. Dead letters require a valid intent UUID, exhausted attempt count and the fixed failure reason.                                                                                             |

Terminal failure is an intervention boundary, not an automatic/manual retry API. Future recovery must be an authorized, audited SQL state transition, preserve the failure identity/history, serialize competing operators, and recheck current references and ownership before another deletion. It must not reset attempts through Bull Board or reuse object keys. Support-ticket creation/linkage remains deferred. Keep terminal SQL/DLQ records and ownership tombstones; no new purge policy is introduced here.

Regression coverage includes bounded Redis/provider waits, queue-state loss with a partially spent SQL budget, forced terminal-job retry, malformed jobs, reference checks, deletion-completion rollback, late provider writes, uncertain HTTP PUT retry/replay, and committed replacement under cleanup exhaustion. These tests use disposable MySQL/Redis and fake storage; provider behavior outside the configured deadline/grace assumptions still requires operational monitoring and bucket inventory.

## Audit and replay consistency

Success audits represent committed domain/security mutations, not every HTTP retry. Identical completed keyed retries return historical responses without new success audits or storage mutations. Failed, stale, and unauthorized actions must not create success events.

Registration confirmation emits registration rather than an extra sign-in event; refresh intentionally has no success audit. Test counts should filter by event/subject or compare against a baseline because authentication/setup can create legitimate events. Request IDs correlate attempts; they do not deduplicate writes.

## Recovery procedures

- **Redis unavailable:** durable SQL email/deletion intents survive. Restore Redis, then allow existing dispatchers to republish eligible work with stable identities. Do not manually duplicate payloads. Legacy queue-only jobs do not have this SQL recovery guarantee.
- **Email failure/expiry:** inspect delivery ID, state, expiry, and sanitized failure metadata. Restore provider configuration before retrying eligible pending work. Cancelled/expired challenge emails must not be sent; the user needs a fresh challenge.
- **Storage terminal failure:** retain the SQL intent and DLQ identity. Inspect current references and ownership before intervention. There is no operator retry API yet; Bull Board retries do not reset terminal SQL state or budgets.
- **Ambiguous upload/crash:** preserve reservations and never-reused keys. Allow grace-based reconciliation; do not delete an object merely because an HTTP response was lost.
- **Database restore/rollback:** preserve compatible outbox/idempotency data, encryption secrets, and ownership fences. Check object/database consistency before restarting workers; see [deployment recovery](deployment.md#persistence-sizing-backups-and-rollback).

Use IDs and fixed reason codes for diagnostics; never dump encrypted or decrypted email bodies, OTPs, tokens, cookies, or replay response payloads. Legacy email/DLQ compatibility still needs privacy cleanup; see [known gaps](backlog.md#verified-implementation-gaps).

## Privacy and rollout boundaries

Idempotency responses can retain account/profile PII for the replay window. Restrict database and backup access and include those records in privacy/erasure procedures. Expiry sweeps and Bull age-based removal are not immediate physical erasure; Bull cleanup is opportunistic and backups/legacy queues require their own policy.

Keep the same stable `CRYPTO_SECRET` across API and worker replicas while encrypted email intents remain. Drain them or introduce explicit key-version migration before rotation. Do not drop live outbox/idempotency tables during application rollback.

Before rollout, require complete CI for the exact commit, a verified backup, all pending migrations, and updated client retry/CORS contracts. In staging check permission loss on replay, old refresh rejection, queue/provider outage recovery with stable delivery IDs, expired challenge cancellation, and healthy readiness. Use test identities only.

The detailed regression map is in [Testing](../test/TESTING.md). Periodic operational monitoring and support-ticket automation are intentionally deferred; the existence of a DLQ does not itself route an alert or create a ticket.
